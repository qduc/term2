# Lens report: architecture
Codebase: /Users/qduc/src/term2  |  Scope: whole repo (source/)  |  Date: 2026-08-01

## Summary
The turn-execution and approval pipeline is deeply layered (`ConversationService` → `ConversationAdapter` → `TurnCoordinator` → `TurnWorkflow` → provider registry), and most layers earn their keep — each adds a real decision (queueing, status validation, retry/recovery, streaming). The composition root (`session-composition.ts`) wires ~25 collaborators cleanly and the invariants around `subagent-manager.ts` as a pure facade hold up under inspection. The weak spots are concentration, not absence, of decomposition: `TurnWorkflow` and `ApprovalFlowCoordinator` each grew one large control-flow/decision method that keeps absorbing new special cases instead of being split along the domain concepts (turn-outcome kind, approval-answer kind) they already model as types elsewhere in the codebase. A generic, persistence-aware `QueueController` was built with a command surface its one production caller never uses, and three independent state representations of "is a turn/approval in flight" (turn status machine, queue phase, adapter-local bookkeeping) require the adapter to manually keep them in sync at every transition.

## Findings

### F-architecture-001: `QueueController`'s generic command/state surface is unused by its only production caller
- **Severity**: low
- **Confidence**: high
- **Location**: `source/services/queue/queue-controller.ts:98-175` (command/driver/preflight surface); `source/services/conversation/conversation-adapter.ts:164-190` (sole production instantiation)
- **Claim**: `QueueController` is a fully general, versioned, persisted state machine (typed branded IDs, `preflightEvaluator`, `completionBarrier`, `ask_user` action kind, `edit_queued`, `answer_preflight`, `change_execution_settings`/`change_cosmetic_settings` commands), but its only production consumer (`ConversationAdapter`) exercises a small subset: `submit`, `cancel`, `resume_queue`, `discard_queue`, `remove_queued`, `resolve_tool_approval`, and the `completed`/`failed` events. `preflightEvaluator`, `completionBarrier`, `ask_user_requested`/`answer_ask_user`, `edit_queued`, and both `change_*_settings` commands are never invoked outside `queue-controller.test.ts`.
- **Evidence**: `grep` for `QueueController` importers outside tests returns only `conversation-adapter.ts`. `grep` for `edit_queued|change_execution_settings|change_cosmetic_settings|answer_preflight` outside `queue-controller.ts`/tests returns nothing. The adapter's `QueueController` construction (lines 179-187) passes only `driver`, `snapshotFactory`, `capacity`, `persistence` — no `preflightEvaluator` or `completionBarrier`.
- **Verify by**: `grep -rn "preflightEvaluator\|completionBarrier" source --include="*.ts" | grep -v test` — confirms zero production wiring. Confirm no second caller exists by `grep -rln "QueueController" source --include="*.ts" | grep -v test.ts`.
- **Invariant impact**: none directly; extends the "largest non-test files" list context (`queue-controller.ts` is not on that list but is comparable in structural weight to the files invariants flag for closer look).

### F-architecture-002: `TurnWorkflow` remains a ~1100-line control-flow monolith despite 20 injected collaborators
- **Severity**: medium
- **Confidence**: high
- **Location**: `source/services/session/turn-workflow.ts:64-99` (`TurnWorkflowDeps`, 20 fields), `:652-768` (`executeContinuationAttempt`, ~118 lines), `:215-402` (`executeInitialAttempt`, ~190 lines), `:914-1003` (`#executeContinuationStreamCycle`)
- **Claim**: The extraction that produced `attemptFactory`, `inputPreparer`, `streamProcessor`, `recoveryHandler`, `planApplier`, `continuationRecoveryHandler`, and `batchCoordinator` moved leaf-level policy and I/O concerns out of `TurnWorkflow`, but the actual branching control loop — the `while(true)` retry/approval/recovery cycle that decides what happens next — is still implemented directly inside `TurnWorkflow`'s own methods, not delegated to any of its 20 collaborators.
- **Evidence**: `executeContinuationAttempt` (lines 652-768) contains a live `while (true)` loop directly inlining generation-staleness checks, parallel-approval batching, stream-cycle dispatch, approval-outcome handling, and a `catch` block calling `#handleContinuationRecovery` with three-way branching (`terminated` / `stale` / `fresh_start` / implicit `resume`) — none of this sequencing is itself delegated; the collaborators are called *from* this loop, they don't own it.
- **Verify by**: Read `turn-workflow.ts:652-768` and confirm the control flow (not just the leaf calls) lives in the method body. Cross-check `TurnWorkflowDeps` (lines 64-99) has 20 fields, none of which is "a class that owns this loop."
- **Invariant impact**: touches the "largest non-test files" note (`turn-workflow.ts` ~1092 lines, already flagged as a candidate for closer look, not pre-judged) — this finding is the closer look, confirming the size reflects concentrated control-flow complexity, not merely verbose leaf logic. Also relevant to `docs/plans/provider-bug-sweep.md` history: real regressions (dropped tool calls, wrong continuation state) were found in exactly this kind of turn-continuation logic, consistent with a file where every new outcome/recovery kind must be threaded through one shared loop.

### F-architecture-003: `ApprovalFlowCoordinator.prepareContinuation` is a single ~180-line function absorbing every approval-answer kind via ad hoc branching
- **Severity**: medium
- **Confidence**: medium
- **Location**: `source/services/approval/approval-flow-coordinator.ts:138-320`; answer-kind type guards defined separately in `source/contracts/conversation.ts:16-45` (`DeniedReadApproveAnswer`, `DockerHostControlApproveAnswer`, plus inline `isReadFileSessionApproveAnswer`)
- **Claim**: Three (at least) distinct "approval answer" kinds — generic `y`/`n`, denied-read (`allow-once`/`allow-remember`/`unsandboxed-once`), docker-host-control (`docker-allow-once`/`docker-allow-session`/`docker-allow-project`), and read-file-session — are each already modeled as their own typed enum/guard in `contracts/conversation.ts`, but `prepareContinuation` does not dispatch on kind through a shared shape; it sequentially computes `deniedReadDecision`, `dockerDecision`, `isDockerRequest`, `allowReadFolderForSession` as independent booleans and interleaves their side effects (folder-allow grants, docker grants, execution overrides, rejection-message construction) in one linear function body.
- **Evidence**: Lines 151-188 compute four independent boolean/kind checks before combining them into one `isApproved` expression; lines 190-238 then contain per-kind side-effecting blocks (denied-read override staging, docker grant) inside the single `if (isApproved)` branch, with docker's rejection path duplicated again at lines 298-301 in the `else` branch. No `Map<AnswerKind, Handler>` or per-kind class exists; each new answer kind so far has been added as another branch in this same function.
- **Verify by**: Diff the git history of `approval-flow-coordinator.ts` around each of the three answer-kind additions (denied-read, docker-host-control, read-file-session) to confirm each was a same-function edit rather than a new handler registration. Compare against `services/approval/approval-decision-policy.ts`, which *does* model "decide" as a clean one-method interface (`ApprovalDecisionPolicy`) — that interface is used for the pre-prompt auto-approve gate, not for `prepareContinuation`'s post-answer application logic, so the clean seam that exists for one half of approval handling was not carried over to the other half.
- **Invariant impact**: "Approval decisions belong in `services/approval/`" — satisfied at the file/module level; this finding is about internal shape within that module, specifically that the module's own `ApprovalDecisionPolicy` abstraction (clearly designed for exactly this kind of variant dispatch) was not reused for the answer-application side.

### F-architecture-004: Two independently-designed approval subsystems (pre-execute interruption vs. post-execute promise-gate) require the adapter to manually keep both in sync
- **Severity**: low
- **Confidence**: medium
- **Location**: `source/services/conversation/conversation-adapter.ts:551-688` (`handleApprovalDecision`, branches on `this.#postExecuteApproval` vs `this.#approval.getPending()`); `source/services/session/post-execute-pending-registry.ts`; `source/services/session/post-execute-pause-policy.ts`; `source/services/approval/approval-state.ts` / `approval-flow-coordinator.ts`
- **Claim**: The codebase has two structurally different approval mechanisms — a pre-execute one that pauses the SDK's own interruption/resume protocol (`ApprovalState`, `ApprovalFlowCoordinator`), and a post-execute one that gates at the tool-execution boundary via a promise the tool call itself awaits (`PostExecutePendingRegistry`, `createPostExecutePausePolicy`). `ConversationAdapter.handleApprovalDecision` must check both (`postExecuteApproval` local field first, then `this.#approval.getPending()`) and route to different continuation entry points (`continueAfterPostExecuteApproval()` vs `continueAfterApproval()`).
- **Evidence**: `conversation-adapter.ts:556-578` handles the post-execute path (snapshot/epoch/revision matching, `decidePostExecutePending`) before falling into the pre-execute path at line 580 onward; `#postExecuteApproval` is set/cleared independently in three places (`#executeMessage` line 545, and twice in `handleApprovalDecision` lines 577 and 654).
- **Verify by**: Trace a tool that uses `createPostExecutePausePolicy` (e.g. denied-read escalation) end-to-end against a tool that uses the SDK interruption path (e.g. `shell` approval) and confirm they surface through different code paths in the same adapter method rather than a shared "pending approval" abstraction.
- **Invariant impact**: none directly named, but relevant to future changes near approval — the invariants doc's open item "reasoning effort no-ops" and the general provider-bug-sweep history suggest this area (session/turn/approval boundary) is actively touched; a third approval-shaped feature would need to decide which of the two existing patterns (or a third) to extend.

## Non-findings
- `subagent-manager.ts` matches the invariant exactly: it contains no execution/prompt/cache/tool-policy logic; every public method is a one-line delegation into `#runtime.<x>` (`source/services/subagents/subagent-manager.ts`). `runtime.ts` correctly composes `mentor-runner.ts`, `execution-runner.ts`, `nested-runner.ts`, `tool-policy.ts` per the documented split.
- `ConversationService` is genuinely a thin facade (`source/services/conversation/conversation-service.ts`) — every method is a one-line forward to `#runtime` or `#adapter`; no orchestration logic leaked in.
- `non-interactive.ts` genuinely shares the conversation runtime with the interactive path via `createConversationRuntime` and a duck-typed `ConversationSessionLike` interface — not a parallel reimplementation.
- UI boundary holds: `grep` for `services/session`/`services/conversation` imports in `components/` found only `StatusBar.tsx` and `BottomArea.tsx`, and in both cases the import is `type`-only (`CodexRateLimitInfo`/`CodexRateLimitWindow` from `conversation-events.js`), not transport or orchestration logic — consistent with the invariant's stated exception pattern, just extended from `providers/` labels to one conversation-event type import.
- `AgentRuntime` / `compose-agent-runtime.ts` (the typed one-shot-agent SDK layer) is not orphaned scaffolding: it is consumed by `run_agent_workflow` (`source/tools/run-agent-workflow.ts`, registered in `agent.ts:477`) via `workflow-evaluator.ts:199`, and by `lib/agent-configuration.ts:212`.
- `registry.ts`'s `createApplicationCompatibilityRunner` (wrapping the new `ApplicationRunLoop` in a `LegacyRunner`-shaped object) is the same kind of intentional transitional bridge the invariants doc already names for `agents-model-bridge.ts` — consistent, not a new problem.
- Queue persistence (`queue-persistence.ts`) uses synchronous `fs` writes with temp-file-then-rename per state transition. Given no stated scale assumptions beyond "single-user local terminal CLI," and that transitions are per-user-action (not per-token), this is proportionate — flagged and dismissed, not a caching/consistency concern.
