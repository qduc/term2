# Lens report: correctness
Codebase: /Users/qduc/src/term2  |  Scope: whole repo (source/)  |  Date: 2026-08-01

## Summary
The codebase is disciplined about generation tokens, staleness checks, and explicit comments explaining
non-obvious safety decisions (especially in `codex-responses-model.ts` and the approval flow), which
made it hard to find outright crashers. The real findings are subtler: a queue-controller failure path
that is provably dead code in production and diverges in recovery semantics from the path that actually
runs, a documented DI boundary (provider registry) that is bypassed by a direct service-module import in
four provider files, and a lock-conflict detection mechanism (`isConversationLocked`, the `'locked'`
status variant) that is fully wired in its type signature but never reached by any caller — the real lock
handling lives entirely in a different, parallel code path. None of these are found to cause visible
breakage today because the paths they cover are unexercised or the workaround is functionally harmless,
but each represents self-consistent wrongness: code, comments, and tests all agree with a design that
production never actually uses.

## Findings

### F-correctness-001: QueueController's `driver.start()`/`continueAfterAction()` catch-and-recover paths are dead code in production and use different recovery semantics than the path that actually runs
- **Severity**: medium
- **Confidence**: high
- **Location**:
  - `source/services/queue/queue-controller.ts:521-541` (`#acceptPreflight`), `:590-628` (`#dispatch`), `:501-519` (`#resolveAction`)
  - `source/services/conversation/conversation-adapter.ts:165-166` (driver wiring), `:407-430` (`#startQueuedTurn`), `:440-473` (`#runQueuedTurn`)
- **Claim**: The `try { await this.#driver.start(active) } catch { this.#queue.unshift(item); ...; pauseReason = 'failure' }` blocks in `QueueController` can never execute against the production driver, because `conversation-adapter.ts`'s `start: (execution) => this.#startQueuedTurn(execution)` is a synchronous `void`-returning function that never throws — it fires `#runQueuedTurn(execution)` without awaiting or returning it, and `#runQueuedTurn` unconditionally catches its own errors (line 467-472) and reports failure via `await this.#queue!.event({ kind: 'failed', ... })` instead. The two failure paths have different recovery behavior: the (dead) `catch` around `driver.start()` re-queues the failed item at the front of the queue (`this.#queue.unshift(item)`) so it is retried automatically; the (live) `event.kind === 'failed'` handler (`queue-controller.ts:473-487`) drops the failed item and does not retry it. Likewise `#resolveAction`'s `if (this.#driver.continueAfterAction)` guard (line 507) is never true for the production driver — `conversation-adapter.ts` has no `continueAfterAction` implementation; approval continuation instead goes through `this.#turnFlow.continueAfterApproval(...)` directly (`conversation-adapter.ts:611-623`), bypassing the queue driver abstraction entirely and reporting outcomes back via `queue.event(...)`.
- **Evidence**: `#startQueuedTurn` (conversation-adapter.ts:407) has no `async` keyword and no `return` statement; `#runQueuedTurn`'s try/catch (line 442-472) is the only place errors from a queued turn are ever surfaced, always via `queue.event({kind:'failed',...})`. `grep` across `source/` shows `continueAfterAction` has zero implementations outside its type declaration and one unrelated test double (`queue-controller.test.ts:1436`, which supplies a driver used only in that one isolated test, not the app's driver). No test in `queue-controller.test.ts` makes `driver.start` throw/reject.
- **Verify by**: Search `source/services/queue/queue-controller.test.ts` for any case where the `start` function passed to `driver` throws or returns a rejected promise — none exists. Then trace `conversation-adapter.ts:165` forward to confirm `start` is the only driver method definition and it has no `continueAfterAction`.
- **Invariant impact**: Not a listed invariant directly, but touches the turn lifecycle path called out in "Already-verified structural facts" (`QueueController` turn admission). If a future refactor makes `#startQueuedTurn` `async` and lets it throw (a natural-looking simplification), the failure-recovery behavior silently changes from "drop failed item" to "auto-retry failed item," with no existing test catching the change either way.

### F-correctness-002: Four provider files import a service module value directly (`NULL_SESSION_CONTEXT_SERVICE`), contradicting the documented provider-registry DI rule
- **Severity**: low
- **Confidence**: high
- **Location**: `source/providers/openai.provider.ts:11`, `source/providers/codex.provider.ts:19`, `source/providers/openrouter.provider.ts:7`, `source/providers/openai-compatible.provider.ts:3` — all `import { NULL_SESSION_CONTEXT_SERVICE } from '../services/session/session-context-service.js';`
- **Claim**: The invariant states `ProviderDeps` exists "specifically so providers avoid importing services directly ... do not 'fix' this by having a provider import a service module directly," yet these four files import a concrete value (not just a type) from `services/session/session-context-service.js` and use it as `sessionContextService ?? NULL_SESSION_CONTEXT_SERVICE` to backfill the optional DI parameter.
- **Evidence**: e.g. `openai.provider.ts:108`: `deps: { loggingService, sessionContextService: sessionContextService ?? NULL_SESSION_CONTEXT_SERVICE }`. The same pattern repeats in `codex.provider.ts:761`, `openrouter.provider.ts:31`, `openai-compatible.provider.ts:91`.
- **Verify by**: `grep -n "NULL_SESSION_CONTEXT_SERVICE" source/providers/*.ts` and confirm each is a value import, then check `source/services/session/session-context-service.ts` exports it as a plain stateless object literal (it does — no constructor, no I/O), so this does not currently create the ESM circular-import risk the DI rule exists to prevent (that file only imports `node:async_hooks` and a type). The violation is of the stated boundary, not (currently) of the risk the boundary defends against.
- **Invariant impact**: Directly touches "New providers must be registered through the provider registry ... do not 'fix' this by having a provider import a service module directly" in invariants.md. Low severity because the imported value is a stateless null-object with no live service state and no import cycle back into `providers/`, but it is the exact pattern the invariant calls out to flag if reintroduced. A local null-object constant defined inside `providers/` (or passed by the registry itself) would close this without behavior change.

### F-correctness-003: `isConversationLocked()` and the `'locked'` variant of `LoadConversationForProjectResult` are unreachable — real lock-conflict detection lives in a separate, inconsistent mechanism
- **Severity**: low
- **Confidence**: high
- **Location**: `source/services/conversation/conversation-persistence.ts:19-23` (type), `:198-218` (`loadConversationForProject`, never returns `'locked'`), `:240-250` (`isConversationLocked`, exported, never called outside its own test)
- **Claim**: `LoadConversationForProjectResult` documents a `'locked'` status as part of its public contract, and a dedicated `isConversationLocked()` function exists to detect it, but no code path ever produces or consumes either — `loadConversationForProject` only ever returns `'not_found' | 'project_mismatch' | 'loaded'`, and `grep` finds `isConversationLocked` referenced nowhere in production code (only in `conversation-persistence.test.ts`). The actual, exercised lock-conflict mechanism is entirely separate: `acquireLock()`/`LockConflictError` in `source/services/logging/conversation-log-writer.ts`, thrown from `logWriter.init()` and caught explicitly in `source/cli.tsx:689-704`.
- **Evidence**: `grep -rln "LockConflictError\|isConversationLocked" source --include='*.ts'` returns only `conversation-log-writer.ts`, `conversation-persistence.ts`, and `conversation-persistence.test.ts` — no call site outside those files, and `LockConflictError` and `isConversationLocked`/`'locked'` never appear together, confirming they are two independent, non-overlapping mechanisms rather than one feature split across two files.
- **Verify by**: `grep -rn "loadConversationForProject" source --include='*.ts'` (zero non-definition matches) and `grep -rn "isConversationLocked" source --include='*.ts'` (only the definition and its dedicated test).
- **Invariant impact**: None directly, but is exactly the "decision-debt" category the audit ground rules call for: a fully-typed, fully-implemented, fully-tested code path with no caller, sitting alongside a separately-implemented mechanism that does the same job differently (`isConversationLocked` returns a synthetic `{pid:-1,...}` on unparseable lock files and never checks pid liveness or staleness, unlike the fork-suggesting UX at `cli.tsx:692-701`, which is the one users actually see).

## Non-findings
- Provider-registry override protection (`registerProvider` throws on duplicate id unless `allowOverride`) is enforced consistently; `upsertProvider`/`unregisterProvider` are the only bypasses and are clearly scoped to runtime-defined providers and test cleanup.
- `SubagentManager`'s mentor-concurrency guard is symmetric: the synchronous `run()` path checks both its own `#mentorActive` flag and `asyncRegistry.hasActiveRunForRole('mentor')`; `startRunAsync()` checks `#mentorActive`, and `SubagentAsyncRegistry.startRun()` independently guards against a second active run sharing the same `role:mentor` session key. Traced both directions (sync-then-async, async-then-sync) and found no window where a second mentor session could start concurrently.
- `SubagentManager` itself (`source/services/subagents/subagent-manager.ts`) is a genuine thin facade — every public method delegates to `#runtime.{mentorRunner,executionRunner,nestedRunner,asyncRegistry}`; the only local state (`#mentorActive`) is a guard flag, not execution/prompt/cache/tool-policy logic, consistent with the invariant.
- `createAiSdkStreamedModel`'s `stream()` (`source/providers/ai-sdk-streamed-model.ts:63-171`) correctly refuses to synthesize a successful completion from an incomplete stream: it throws if `finish.finishReason.unified === 'other'` with no native raw reason, throws if no response id was ever observed, and throws if the stream ends without a `finish` event at all (line 170) — consistent with the provider-bug-sweep's "must not turn a missing terminal event into empty success" requirement.
- `retry-error-classification.ts`'s logging catch (`logWebSocketCloseCode`, line 82-95) is a deliberately-scoped no-op with an explicit comment ("Logging should never affect retry classification") — the one bare catch I inspected in depth that is self-documenting and correct rather than a silent-swallow risk.
- `ApprovalFlowCoordinator.prepareContinuation` correctly special-cases Docker host-control approvals so that a generic "y" answer cannot resume a Docker grant it wasn't meant for (`isDockerRequest ? dockerDecision : ...`), and deliberately leaves the pending block in place after a Docker grant with an explanatory comment for why `execute()` still needs it.
