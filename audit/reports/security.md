# Lens report: security
Codebase: /Users/qduc/src/term2  |  Scope: whole repo (source/)  |  Date: 2026-08-01

## Summary
Two findings are severe and concrete: provider API keys sourced purely from environment variables get written in plaintext into `settings.json` on first run (no user action required), and every file-mutating tool (`create_file`, `search_replace`, `apply_patch`) decides "inside workspace, auto-approve" using a purely lexical path check that a pre-planted symlink defeats, letting the model write to any path the process can reach without a human ever seeing an approval prompt. Two more findings concern the shell sandbox/approval boundary itself: it fails open (unsandboxed, unapproved execution) under a specific TOCTOU race, and an opt-in auto-approval mode lets a secondary LLM — not the user — authorize unsandboxed host-level command execution, which directly contradicts the tool description shown to the primary model. `pnpm audit` turned up production-path DoS CVEs, none of which are RCE-level. `audit/invariants.md` did not exist at the start of this pass, so findings below were derived and cross-checked directly against source, not against a pre-verified ground truth document.

## Findings

### F-security-001: Environment-sourced API keys are persisted to plaintext settings.json on first run
- **Severity**: critical
- **Confidence**: high
- **Location**: `source/services/settings/settings-service.ts:92` (`disableFilePersistence = ... ?? isTestEnvironment()`), `:170-185` (auto-creates `settings.json` from merged settings when no config file exists yet), `source/services/settings/settings-merger.ts:58-140` (`mergeSettings` folds `env` directly into the object that gets saved), `source/services/settings/settings-env.ts:18,44,47,54` (`OPENROUTER_API_KEY`, `TAVILY_API_KEY`, `EXA_API_KEY`, `OPENAI_API_KEY` env vars map into `agent.openrouter.apiKey`, `webSearch.tavily.apiKey`, `webSearch.exa.apiKey`, `agent.openai.apiKey`), `source/services/settings/settings-persistence.ts:83-155` (`stripSensitiveSettings` only deletes `agent.openrouter.baseUrl/referrer/title` and `app.shellPath` — no `apiKey` field is ever stripped), `source/services/settings/settings-schema.ts:409-416` (`SENSITIVE_SETTING_KEYS` used to block direct `set()` of a field is a *different*, unrelated 4-item list, also missing every `apiKey`).
- **Claim**: A user who only ever sets `OPENAI_API_KEY`/`OPENROUTER_API_KEY`/`TAVILY_API_KEY`/`EXA_API_KEY` as shell environment variables (never through any settings UI) will, on first launch, have that key written verbatim into `settings.json` on disk, and it will be rewritten there on every subsequent `set()` call for any unrelated setting, because the object handed to `saveSettingsToFile` is the full env+file+cli-merged `this.settings`, and the "strip sensitive settings before persisting" function does not know `apiKey` is sensitive.
- **Evidence**: `settings-service.ts:173-176` states the intent explicitly: *"If there was no config file on disk, persist the current merged settings so users get a settings.json created at startup."* `this.settings` at that point is the output of `mergeSettings(DEFAULT_SETTINGS, fileConfig, env, cli, ...)`, which deep-merges `env` (containing any of the four apiKey fields above) into the object that becomes `settings.json`. `stripSensitiveSettings` (settings-persistence.ts:134-155) is the single point meant to prevent secrets reaching disk, but its full body only touches `agent.openrouter.{baseUrl,referrer,title}` and `app.shellPath` — it was evidently written for provider config hygiene, not credential hygiene, and nobody extended it when apiKey fields were added to the schema (`agent.openrouter.apiKey`, `agent.openai.apiKey`, `webSearch.tavily.apiKey`, `webSearch.exa.apiKey` — settings-schema.ts:96,104,322,327,371). Neither `saveSettingsToFile` nor `mkdirSync`/`writeFileSync` calls in settings-persistence.ts pass a restrictive `mode`, so the resulting file inherits the process umask (typically 644 — world-readable on a shared host).
- **Verify by**: In a clean settings dir, `export OPENROUTER_API_KEY=sk-test-123 && node dist/cli.js` (or run any flow that constructs `SettingsService` with `disableFilePersistence` left default/false and no pre-existing settings file), then `grep -n apiKey <settingsDir>/settings.json` and confirm the literal key value is present; check `ls -l <settingsDir>/settings.json` for world-readable permissions.
- **Invariant impact**: none (no invariants.md was present to check against).

### F-security-002: File-mutating tools resolve the workspace-boundary approval check lexically, not via realpath — a planted symlink bypasses human approval for out-of-workspace writes
- **Severity**: critical
- **Confidence**: high
- **Location**: `source/tools/utils.ts:10-74` (`resolveWorkspacePath` uses `path.resolve`/`path.normalize` only, never `fs.realpathSync`), `source/tools/file/create-file.ts:102-118` (`needsApproval` auto-approves when `targetPath.startsWith(cwd + path.sep)`), `:156-179` (`execute` calls `writeFile`/`mkdir` on that same lexical path), `source/tools/file/search-replace.ts:282-368` (`needsApproval`, same `insideCwd` string check, and it even `readFile`s through the symlink to compute match info) and `:516-596` (`execute` writes through the symlink), `source/tools/file/apply-patch.ts:212-314` (`needsApproval` `insideCwd` check) and `:332-432` (`writeFileFn` writes through the symlink).
- **Claim**: If a symlink already exists inside the workspace whose target resolves outside it (e.g. `workspace/link -> ~/.ssh/authorized_keys` or `~/.bashrc`), any of `create_file`, `search_replace`, or `apply_patch` invoked against the path `link` is auto-approved (no human prompt) because the containment check is purely lexical, and the subsequent `fs.writeFile`/`fs.readFile`/`fs.mkdir` calls follow the symlink at the OS level, letting the model write arbitrary content to the real target with zero approval.
- **Evidence**: `resolveWorkspacePath` (tools/utils.ts) never calls `fs.realpathSync`; it is a pure string operation. All three tools' `needsApproval` functions compute `insideCwd = targetPath.startsWith(cwd + path.sep)` on that lexical result and return `false` (auto-approve) when true. Their `execute` functions then call Node's `fs.promises.writeFile`/`readFile`/`mkdir`, all of which follow symlinks by default — there is no `lstat` or symlink check anywhere in `source/tools/file/`. `create_file`'s `overwrite: true` path (create-file.ts:156-179) is the cleanest exploit: no confirmation code is required when `overwrite=true` is passed directly (comment at :159-162: *"overwrite=true is used without a code, overwrite directly regardless of stale pending entries"*), so a single tool call fully rewrites the symlink target's file. `search_replace`'s `needsApproval` (search-replace.ts:310-330) even reads the real target file's content through the symlink to compute a match, meaning the model can also use it to confirm existing content of files it isn't nominally allowed to touch before deciding whether to auto-approved-overwrite them.
- **Verify by**: With a workspace tool session, create a symlink `workspace/pwn -> $HOME/.bashrc` (e.g. via an approved or sandboxed shell `ln -s` call — `ln` is not specially classified by `source/utils/shell/command-safety`), then call `create_file` with `path: "pwn"`, `overwrite: true`, and arbitrary content. Confirm the tool returns `Overwrote pwn` without any approval prompt, and that `$HOME/.bashrc` now contains the new content.
- **Invariant impact**: none (no invariants.md present); this directly undermines the "workspace boundary" concept that `needsApproval` in all three tools claims to enforce (see their own comments, e.g. create-file.ts:124-126: *"The workspace boundary was already enforced by needsApproval"*).

### F-security-003: Sandboxed shell execution never runs the dangerous-command classifier and skips `needsApproval` entirely, with a process-wide static failure flag creating a fail-open TOCTOU into unsandboxed, unapproved execution
- **Severity**: high
- **Confidence**: medium
- **Location**: `source/tools/system/shell.ts:338-350` (`needsApproval`: `if (availability.type === 'available') return false;` — skips `isMutatingCommand` entirely whenever the sandbox is available), `:479-526` (`execute` re-checks `shellSandboxRunner.availability()` independently and, when not `'available'`, "warns and runs command without sandbox" — i.e. fails open), `source/utils/shell/sandbox/shell-sandbox-runner.ts:11-12,25-30,56-78` (`#initializationFailure` and `#initializedForKey` are `static` — shared process-wide across every concurrent shell tool call and every session in the process).
- **Claim**: The decision "this command needs no human approval because it will run in the sandbox" (made in `needsApproval`) and the decision "the sandbox is actually available right now" (re-checked independently in `execute`) can diverge, because sandbox availability is backed by mutable class-static state (`AnthropicShellSandboxRunner.#initializationFailure`) that a concurrent shell call's failed `wrap()` can flip between the two checks; when that happens the command executes fully unsandboxed with no approval prompt at all, for any command including ones the classifier would mark RED.
- **Evidence**: In `needsApproval` (shell.ts:338-350), when `!sshService && sandboxEnabled`, the function returns `false` purely based on `shellSandboxRunner.availability()` being `'available'` — `isMutatingCommand`/`validateCommandSafety` is never called on this path (it's only reached in the `else` branch, i.e. no-sandbox mode). In `execute` (shell.ts:479-526), `sandboxAvailability` is fetched again independently; if it is no longer `'available'` (any of `unsupported_platform | missing_dependency | initialization_failed`) but also not `'disabled'`, the code logs `'Shell sandbox unavailable; running command without sandbox'` and proceeds to run the raw command with `env: undefined` (no sandbox restrictions) — `sandboxed` stays `false`, so `executeShellCommandImpl` runs without the sandbox's network/write/read restrictions. `AnthropicShellSandboxRunner.#initializationFailure` (shell-sandbox-runner.ts:12) is a `static` field shared by every shell tool call in the process; a `wrap()` failure from an unrelated concurrent command sets it (`:73-76`) and it persists until the next successful `#initialize()`, meaning `availability()` calls from other in-flight commands can flip from `'available'` to `'initialization_failed'` in the window between one command's `needsApproval` and its own `execute`.
- **Verify by**: Unit/integration-test the race directly: stub `shellSandboxRunner.availability()` to return `{type:'available'}` on the first call (used by `needsApproval`) and `{type:'initialization_failed', reason:'x'}` on the second call (used by `execute`), then assert the command executes with `env: undefined` (no sandbox) and no approval prompt was raised — this exercises exactly the code path at shell.ts:479-526's `else if (sandboxAvailability.type !== 'disabled')` branch reached after `needsApproval` already returned `false`.
- **Invariant impact**: none on file (no invariants.md present); worth confirming with the team whether "sandboxed commands skip approval by design" (which is clearly intentional given the `SANDBOX_ESCAPE_INSTRUCTION` messaging) was meant to also cover the fail-open-to-unsandboxed branch, or whether that branch should require approval when it silently drops sandboxing.

### F-security-004: `shell.autoApproveMode = 'auto'` lets a secondary LLM approve unsandboxed (full host access) shell commands with zero human confirmation, contradicting the tool's own approval contract
- **Severity**: high
- **Confidence**: medium
- **Location**: `source/services/approval/shell-auto-approval-resolver.ts:47-55` (`isUnsandboxedApprovalEligible`, `shouldAutoApprove`), `source/services/approval/shell-sandbox-approval.ts:36-64` (`requiresHumanShellApproval`: `if (isUnsandboxedShell(...) && !opts?.llmMayEvaluateUnsandboxed) return true;` — the human-forcing gate is explicitly lifted), `source/services/approval/tool-approval-batch-coordinator.ts:111-152` (wires `llmMayEvaluateUnsandboxed: shellAutoApproval.isUnsandboxedApprovalEligible()` into the gate and, if not forced, routes to `ShellAutoApprovalDecisionPolicy`), `source/services/approval/approval-decision-policy.ts:21-30` (`ShellAutoApprovalDecisionPolicy.decide` returns `'approve'` straight from the LLM advisory), `source/tools/system/shell.ts:64-66` (tool description told to the primary model: *"unsandboxed... requires explicit user approval"*), `source/utils/shell/sandbox/sandbox-policy.ts:554-555` (`SANDBOX_ESCAPE_INSTRUCTION`: *"user approval will be required"*). Default is off: `settings-schema.ts:200,864` (`shell.autoApproveMode` defaults to `'off'`).
- **Claim**: With `shell.autoApproveMode` set to `'auto'` (opt-in, off by default) and the sandbox enabled, a shell call using `sandbox: "unsandboxed"` — which both the tool description and the escape-instruction text tell the primary model requires "explicit user approval" — can be fully approved by a separate, cheaper "chore"-tier LLM's own judgment (`shell-auto-approval-evaluator.ts`), with no human ever seeing a prompt, as long as the evaluator doesn't classify the command RED via the static heuristic.
- **Evidence**: `requiresHumanShellApproval` (shell-sandbox-approval.ts:53) normally forces `'prompt'` for any unsandboxed shell call (`isUnsandboxedShell` true) — but the caller can pass `llmMayEvaluateUnsandboxed: true`, which the batch coordinator supplies whenever `shellAutoApproval.isUnsandboxedApprovalEligible()` is true (mode is `'advisory'`/`'auto'` and sandbox enabled — shell-auto-approval-resolver.ts:47-51). When the human-force gate is lifted, the coordinator falls through to `shellAutoApproval.resolveAdvisoryForInterruption`, which asks the "chore" model to approve/deny (shell-auto-approval-evaluator.ts:270+), and `ShellAutoApprovalDecisionPolicy.decide` (approval-decision-policy.ts:24-29) converts an `approved: true` LLM advisory straight into `'approve'` — no human step. The evaluator's own history context (`buildCompactHistoryContext`, evaluator.ts:75-83) is restricted to `user`/`assistant` roles (excludes raw tool output), which is a partial mitigation against direct tool-output prompt injection, but an assistant turn that paraphrases attacker-controlled content (e.g. from a fetched web page) back into its own message is not filtered out.
- **Verify by**: Set `shell.autoApproveMode: 'auto'` with sandbox enabled, drive a conversation where the model calls `shell` with `sandbox: "unsandboxed"` and a YELLOW-but-not-RED command (e.g. something outside the RED pattern list in `command-safety/constants.ts`), and confirm no `approval_required` terminal/UI prompt is ever emitted — the call resolves directly to execution based on the auto-approval model's `approved: true` response.
- **Invariant impact**: none on file; this is an explicit, commented design decision (shell-sandbox-approval.ts:40-44) rather than an oversight, but it is a real widening of what "requires explicit user approval" means in practice, and it is not reflected in the tool description shown to the primary model.

### F-security-005: Production-path dependencies carry known high-severity DoS CVEs
- **Severity**: medium
- **Confidence**: high
- **Location**: `pnpm audit` output (see verify step); `ws` pulled in via `ink` (production dependency — the terminal UI framework), `picomatch` pulled in via `fast-glob` (used by `source/tools/file/glob.ts`), `shell-quote` pulled in via `@anthropic-ai/sandbox-runtime` (the sandbox package this report's F-003 also concerns).
- **Claim**: `pnpm audit` reports 13 high and 5 moderate advisories; of those, at least three are on production (non-dev) dependency paths: `ws` (`>=8.0.0 <8.21.0`, memory-exhaustion DoS from tiny fragments; `>=8.0.0 <8.20.1`, uninitialized memory disclosure) via `ink>ws`; `picomatch` (`<2.3.2`, ReDoS via extglob quantifiers) via `fast-glob>micromatch>picomatch`; and `shell-quote` (`<=1.8.4`, quadratic-complexity DoS in `parse()`, CWE-407) via `@anthropic-ai/sandbox-runtime>shell-quote`. All are DoS/disclosure-of-uninitialized-memory class, not remote code execution.
- **Evidence**: `pnpm audit --json` metadata: `{"info":0,"low":1,"moderate":5,"high":13,"critical":0}`; advisory entries confirm the `dev: false` marking for the three paths above (the remaining high/moderate findings are entirely within `eslint`/`@babel/cli`/`vitest`/`lint-staged` devDependency chains and are lower priority for a shipped-CLI security lens).
- **Verify by**: `pnpm audit --json | jq '.advisories[] | select(.findings[].dev==false) | {module: .module_name, severity, title}'`.
- **Invariant impact**: none.

## Non-findings
- No `eval(`/`new Function(` usage anywhere in `source/` — no dynamic code execution from untrusted strings.
- `sanitizeHeaders` (`source/utils/header-sanitizer.ts`) correctly redacts `authorization|key|cookie|token|secret|signature`-matching header names before they reach `ProviderTrafficArtifactStore`/winston logs, and `source/providers/fetch/logging-middleware.ts` and `codex-responses-model.ts` both route through it before logging headers.
- `sanitizeSentTrafficBody`/`sanitizeReasoningDetails` in `source/services/logging/provider-traffic.ts` truncate long text and strip encrypted-reasoning payloads before writing provider traffic to disk; reasonable content-size hygiene for logs, independent of the header issue above.
- Docker host-control capability (`source/utils/shell/sandbox/docker-host-control.ts` and the `dockerHostControlRequested`/`hasDockerGrant` gating in `shell.ts`) is consistently approval-gated in the code paths read; no path found that grants the Docker socket without an explicit approval or a recorded per-session/per-project grant.
- Sandbox default posture (`createSandboxRuntimeConfig`, `sandbox-policy.ts`) is reasonably conservative: `allowNetworking` defaults `false` (network denied except a curated package-registry allowlist), `readPolicy` defaults `'standard'` (credential files explicitly denied), and writes are constrained to `[workspaceRoot, tmpDir]` with a hardcoded, non-configurable protected-path list (`$HOME`, `/etc`, `/usr`, etc.) that intentionally cannot be weakened via settings.
- `settings.json` schema does correctly avoid persisting `app.shellPath` and `agent.openrouter.{baseUrl,referrer,title}` — the `stripSensitiveSettings` mechanism itself is sound in design, just incomplete in coverage (see F-001).
