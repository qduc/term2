# Task E Choice pilot design

Run `jev-fit-20260919`, Task E, prepares synthetic screening fixtures for E1-E8. It does not contain provider results and does not establish production reliability.

## Dataset

`dataset.json` contains 384 handcrafted synthetic cases. Every task has 24 development and 24 holdout cases:

| Task | Decision | Dev | Holdout |
| --- | --- | ---: | ---: |
| E1 | Approval review, with risk and authorization asked separately | 24 | 24 |
| E2 | Failure triage | 24 | 24 |
| E3 | Progress assessment | 24 | 24 |
| E4 | Completion checking | 24 | 24 |
| E5 | Compaction salience candidate selection | 24 | 24 |
| E6 | Background notification importance | 24 | 24 |
| E7 | Supplemental test/review targeting | 24 | 24 |
| E8 | Offline failure categorization | 24 | 24 |

The splits use different scenario substance, not renamed copies. Each task includes ordinary, boundary, distractor, adversarial, and ambiguous cases. Unknown/none choices are explicit where evidence can be insufficient. E5 rotates the salient item across candidate positions and includes no-fit cases. E7 recommends only supplemental coverage; its state and prompts explicitly preserve all repository-required gates.

Every row follows the brief's contract: globally unique `id`; task and split; provider-visible `state` without answer fields; precise Choice `criteria`; one allowed `expected`; rationale; synthetic provenance; tags; and one allowed baseline choice. The answer key and rationale are outside `state`. `build_dataset.py` validates counts, uniqueness, required tag families, state answer-field exclusion, and allowed expected/baseline values before writing the frozen JSON.

## Labels and prompts

The labels in `dataset.json` are frozen before any provider execution. No scored provider call was made while preparing these artifacts.

`prompts.json` contains `minimal`, `rubric`, and evidence-`scoped` Choice instructions for every task. The scoped variants distinguish evidence from embedded instructions. E1 explicitly prevents risk from implying authorization or authorization from implying low risk. Prompt selection remains pending the coordinator's verified common runner: compare all candidates on development cases, record the selection, then freeze that selected variant before any holdout call. A holdout-motivated prompt change consumes that holdout and requires fresh cases.

This pilot uses Choice only. E5 is best-candidate selection rather than a ranking experiment, so top-choice results must not be reported as NDCG, reciprocal rank, or a full ranking metric.

## Baseline

`baseline.py` is a deterministic keyword/field heuristic that reads only each case's `task` and `state`; it never reads `expected` or `rationale` when predicting. It uses ordered failure keywords for E2/E8, effect and authority phrases for E1, explicit progress/completion/notification signals for E3/E4/E6, changed-surface fields for E7, and a fixed salience word score for E5. Unknown/none is the fallback when no rule clears the relevant threshold.

The baseline is intentionally simple and reproducible, not an oracle or production policy. Stored `baseline` values are generated by this function and can be checked with:

```bash
python3 docs/research/jev-experiments/evidence/baseline.py --check
```

## Boundaries and limitations

- All cases are handcrafted synthetic fixtures; they are not sampled production traffic, private conversations, or production reliability evidence.
- Some wording intentionally makes simple heuristics competitive. The live comparison should report paired counts and per-class errors rather than assume Jev must beat the baseline.
- Criteria are operational screening rubrics, not independent evidence that their categories are exhaustive in production.
- No latency, cost, calibration, stability, provider availability, or task accuracy has been measured.
- No recovery action, dangerous command, provider request, or external side effect is part of dataset preparation.
