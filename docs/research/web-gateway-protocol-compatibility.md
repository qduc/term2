# Web-gateway protocol compatibility research

**As-of date:** 2026-09-19
**Scope:** term2's private gateway and the possibility of using an existing web client. External facts below are linked to first-party specifications, documentation, or source repositories and were checked on the as-of date.

## Recommendation

**Adapt the gateway at a BFF boundary, with AG-UI as the first web interoperability target; keep term2's private gateway as the canonical protocol.** Do not replace the gateway with OpenAI, A2A, MCP, or either ACP. Run a separate ACP v2 adapter experiment only if editor/IDE clients are a product goal; it is a stronger semantic match for coding-agent sessions and permissions, but it is not an existing browser web client. Confidence: **high (0.85)**.

AG-UI is the only candidate in this review whose stated boundary is agent-runtime → user-facing application. Its event vocabulary covers lifecycle, text, tools, state, reasoning, and subagents ([AG-UI overview](https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/ag_ui.md), accessed 2026-09-19; [event reference](https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/sdk/js/core/events.mdx), accessed 2026-09-19). The official JavaScript `HttpAgent` is a useful wire client, and the AG-UI documentation points production users to CopilotKit ([client transport source](https://github.com/ag-ui-protocol/ag-ui/blob/main/sdks/typescript/packages/client/src/agent/http.ts), accessed 2026-09-19; [client guide](https://github.com/ag-ui-protocol/ag-ui/blob/main/docs/quickstart/clients.mdx), accessed 2026-09-19).

That is an **adapter opportunity**, not drop-in compatibility. AG-UI's normal shape is one `POST` carrying `RunAgentInput` and returning an event stream; term2 has authenticated, separate session/message/interaction/command routes and a separate `GET` SSE replay stream. The adapter should live in the existing BFF deployment (consistent with the gateway plan's BFF-only decision), translate AG-UI runs to term2 sessions, and retain term2's approval, workspace, auth, and replay rules.

OpenAI compatibility is a useful secondary, low-fidelity facade for generic chat clients. Open WebUI explicitly requires `/v1/chat/completions` and recommends `/v1/models` for model discovery ([Open WebUI OpenAI-compatible provider guide](https://github.com/open-webui/docs/blob/main/docs/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible.mdx), accessed 2026-09-19). However, that facade cannot faithfully expose term2's approvals, questions, durable event cursor, workspace admission, commands, or per-session policy. It would make a generic chat demo possible, not provide term2 UI parity.

A2A, MCP, and historical ACP should be treated as adjacent protocols: A2A is agent↔agent task interoperability, MCP is host/client↔tool/context interoperability, and ACP was an agent communication protocol that officially merged into A2A. None is a drop-in term2 web UI contract. The ACP maintainers explicitly say active ACP development is winding down and BeeAI now uses A2A ([ACP/A2A announcement](https://github.com/orgs/i-am-bee/discussions/5), accessed 2026-09-19); the ACP repository is archived ([archived repository](https://github.com/i-am-bee/acp), accessed 2026-09-19).

The separate **Agent Client Protocol (ACP v2)** is materially more relevant to coding-agent clients: its official overview defines JSON-RPC methods for initialization, authentication, session creation/resume, prompts, cancellation, permission requests, elicitation, and session updates (including message, tool-call, plan, command, and configuration notifications) ([ACP v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/overview.mdx), accessed 2026-09-19). Its documented clients are typically code editors, and its session setup includes an absolute working directory and additional directory roots ([ACP v2 session setup](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/session-setup.mdx), accessed 2026-09-19). That makes an ACP v2 adapter a worthwhile **separate editor-integration experiment**, not a reason to replace the private HTTP/SSE gateway: the registry catalogs agents, not a browser UI ([ACP registry](https://agentclientprotocol.com/get-started/registry), accessed 2026-09-19), and the protocol's own browser-bridge discussion describes a browser → bridge → JSON-RPC arrangement rather than an unchanged browser client ([browser bridge discussion](https://github.com/agentclientprotocol/agent-client-protocol/issues/1104), accessed 2026-09-19).

## What term2 actually exposes

The following is from the current gateway source, not an inferred REST design:

* `ASSERTION_PURPOSES` in [`source/gateway/contracts.ts`](../../source/gateway/contracts.ts) scopes every operation (`workspace_*`, settings/credentials/OAuth, session lifecycle, message submission, commands, interaction resolution, abort, and event connection). `GatewayServer` in [`source/gateway/server.ts`](../../source/gateway/server.ts) requires `X-Term2-Assertion`, accepts JSON, and serves a Unix socket or TLS network transport. Local-owner settings/credential/OAuth purposes are additionally checked against the configured owner in `Term2Gateway`.
* `matchPrivateRoute` in [`source/gateway/gateway.ts`](../../source/gateway/gateway.ts) maps `/private/agent/v1/workspaces`, workspace-candidate routes, `/models`, `/settings`, credentials/OAuth, `/sessions`, `/sessions/:id/messages`, `/abort`, `/events`, `/config`, `/commands`, and `/interactions/:id`. The legacy `POST /` is only a session-create compatibility alias.
* `FROZEN_AGENT_EVENT_TYPES` in [`source/gateway/persistence/contracts.ts`](../../source/gateway/persistence/contracts.ts) covers user acceptance/rejection, assistant/text/reasoning, tool/command, approval and question interactions, retries, subagents, compaction, usage, and terminal turn events. The public envelope is `{schemaVersion,id,sessionId,type,occurredAt,payload}`.
* `#eventsResponse` in [`source/gateway/gateway.ts`](../../source/gateway/gateway.ts) serves SSE with event `id`, accepts `after` or `Last-Event-ID`, detects mismatched cursors, replays from the durable journal, emits heartbeats, and returns an explicit reload-required response when a cursor was compacted or the journal cannot safely replay it. This is stronger than a live-only token stream.
* `interaction-protocol.ts` projects sanitized, revisioned `tool_approval`, `ask_user`, and `check_in` DTOs. Choices are authoritative (for example, allow once/session, reject, continue/stop); paths, credentials, arguments, and question text are bounded/redacted. Resolution is a separate, revision-checked route.
* Message submission is idempotent through `clientRequestId`, returns an accepted `turnId`, and is admitted to a persisted session. `command_invoke` is allowlisted to `compact`, `retry-tool`, and `retry-turn`; session config can change model, reasoning effort, and mode only while idle. Workspace candidates are validated/browsed/selected before a session binding records root and read/read-write access.

These semantics explain why a model API alone is insufficient: the gateway is a multi-user control plane with filesystem authority, approvals, durable recovery, and session-scoped security, not merely a model completion endpoint.

## Realistic client choices

### Unchanged: none

No reviewed web client can connect unchanged. The gateway requires an assertion in a private transport and binds the assertion purpose and session ID to the URL. The existing BFF-only deployment decision also intentionally keeps the browser away from the gateway. A client expecting OpenAI sends `Authorization: Bearer ...` to `/v1/chat/completions`; AG-UI's `HttpAgent` sends a single `POST` to one agent URL with `RunAgentInput`; A2A clients discover an Agent Card and drive tasks. None speaks term2's route/purpose/assertion protocol.

### Minimal adapter: AG-UI client / CopilotKit

Expose an AG-UI endpoint in the BFF (or a separately authenticated adapter), not a new unauthenticated gateway route:

1. Map `RunAgentInput.threadId` to an existing or newly selected term2 session, after BFF user authorization and workspace selection.
2. Submit the input message through the signed `message_submit` path.
3. Translate durable term2 events to AG-UI lifecycle/text/reasoning/tool/subagent events; use AG-UI `RAW`/`CUSTOM` only for term2-specific command and interaction metadata.
4. On an approval/question, end the AG-UI run with an interrupt outcome and resume only after the BFF maps the user's response to the term2 interaction ID and revision. Never turn an approval into an ordinary user message.
5. Keep a term2 cursor server-side. AG-UI's standard client transport is not currently a drop-in replay client: the official `HttpAgent` source constructs a POST with `Accept: text/event-stream`, while its fetch path does not carry term2's `after`/`Last-Event-ID` contract ([source](https://github.com/ag-ui-protocol/ag-ui/blob/main/sdks/typescript/packages/client/src/agent/http.ts), accessed 2026-09-19). A 2026 AG-UI issue explicitly records native SSE resumption as a missing feature ([issue #1852](https://github.com/ag-ui-protocol/ag-ui/issues/1852), accessed 2026-09-19).

This path could reuse AG-UI's event application and CopilotKit UI for ordinary chat, but term2-specific settings, workspaces, commands, and approval cards still need BFF UI/components or custom events. It is the best first experiment because it preserves the correct agent↔frontend boundary.

### Compatibility facade: OpenAI clients / Open WebUI

An OpenAI facade could map each request to a term2 session and return Chat Completions SSE deltas. Open WebUI's documented required surface is `/v1/chat/completions`, with `/v1/models` recommended for discovery ([official guide](https://github.com/open-webui/docs/blob/main/docs/getting-started/quick-start/connect-a-provider/starting-with-openai-compatible.mdx), accessed 2026-09-19). The official OpenAI API also defines function tool calls in Chat Completions and streamed Responses events ([Chat reference](https://developers.openai.com/api/reference/resources/chat), accessed 2026-09-19; [Responses streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses), accessed 2026-09-19).

This facade is only suitable for a deliberately reduced “chat and text/tool status” mode. It cannot faithfully represent multiple pending interactions, revisioned safe choices, `ask_user` question schemas, session/workspace discovery, replay-compaction reloads, `compact`/retry commands, or term2's assertion purposes. Returning a fake assistant message while an approval is pending would be especially dangerous: the generic client has no way to know whether an operation was authorized or merely paused.

### Separate editor experiment: ACP v2

ACP v2 is the strongest semantic match in this review for an editor or IDE client. Its baseline methods cover initialization, optional authentication, session creation/list/resume/close, prompt, and cancellation; its client-facing methods cover permission requests and optional elicitation; and its session updates cover messages, tool calls, terminal output, plans, available commands, and configuration options ([ACP v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/overview.mdx), accessed 2026-09-19). The session setup model also carries an absolute `cwd` and additional directory roots ([ACP v2 session setup](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/session-setup.mdx), accessed 2026-09-19), which maps more naturally to term2 workspace binding than OpenAI or AG-UI.

The fit is still an adapter, not unchanged reuse. ACP v2 is JSON-RPC and assumes a client-managed coding agent; its documented client role is typically an editor, while term2's browser deployment is a BFF calling a private assertion-protected gateway. The ACP registry lists agents, not a web UI ([registry](https://agentclientprotocol.com/get-started/registry), accessed 2026-09-19). A term2 ACP adapter would therefore need to translate `session/new`/`session/resume`/`session/prompt` and `session/update` to the existing session, message, durable-event, and interaction routes, while keeping assertion creation and workspace authorization inside the BFF. It should be a separate experiment, with editor integration as its go/no-go objective—not a substitute for the AG-UI web experiment.

### A2A, MCP, and historical ACP

* A2A has a strong task lifecycle and official JavaScript client (`@a2a-js/sdk`) ([SDK](https://github.com/a2aproject/a2a-js), accessed 2026-09-19), but its `Task`, `Message`, `Artifact`, context, streaming, and webhook model is for agents communicating with agents. It is a good future outbound/inbound subagent boundary, not a replacement for the term2 web control plane. A2A's own specification describes asynchronous processing and polling/streaming/push task updates ([specification](https://github.com/a2aproject/A2A/blob/main/docs/specification.md), accessed 2026-09-19).
* MCP's architecture deliberately puts a host between user/LLM orchestration and specialized servers; servers expose prompts, resources, and tools, while the host owns policy and context ([MCP architecture](https://modelcontextprotocol.io/specification/2025-03-26/architecture/index), accessed 2026-09-19; [server primitives](https://modelcontextprotocol.io/specification/2025-06-18/server), accessed 2026-09-19). MCP can be valuable for exposing selected term2 capabilities to compatible hosts, but an MCP server is not a browser session/history/settings UI and does not replace the gateway's filesystem admission and assertion model.
* ACP's welcome page describes REST, streaming, long-running tasks, discovery, and `Await`, but its own banner says it is now part of A2A ([ACP welcome](https://agentcommunicationprotocol.dev/introduction/welcome), accessed 2026-09-19). The maintainers' announcement says active development is winding down, BeeAI moved to A2A, and ACP's repository is archived ([announcement](https://github.com/orgs/i-am-bee/discussions/5), accessed 2026-09-19; [archive notice](https://github.com/i-am-bee/acp), accessed 2026-09-19). Do not start an ACP implementation; use A2A migration guidance if agent interoperability becomes a requirement. Neither ACP nor BeeAI's cited material establishes a drop-in term2 web client.

## Semantic loss and security risks

Any compatibility layer must be explicit about what it drops:

* **Authorization loss:** OpenAI/AG-UI tool-call fields do not carry term2's assertion purpose, owner subject, workspace grant version, read-only posture, or interaction revision. A facade must perform those checks before invoking term2 and must not let client-supplied tool arguments select a workspace or bypass the BFF.
* **Approval loss:** Mapping `approval_required` to an assistant tool call or plain text turns “pending authorization” into “model output.” A generic client may auto-submit a result, retry, or display a successful-looking message. Only an explicit adapter-owned approval UI can safely call `interaction_resolve`.
* **Replay loss:** A live AG-UI/OpenAI stream can reconnect from the wrong point or duplicate deltas. Term2's journal has compaction floors and generation checks; an adapter must either preserve cursor semantics or force a session reload. It must never silently replay arbitrary user messages, because term2 admission is idempotent but event application is not interchangeable with model history.
* **Workspace/files loss:** OpenAI file IDs, AG-UI attachments, A2A file parts, and MCP resources are not equivalent to a canonical local root with read/read-write access. Do not accept a remote file URL or path as a substitute for a validated workspace binding.
* **Identity/deployment loss:** Browser clients typically use bearer/session credentials, whereas term2 uses BFF-signed assertions and a private socket/TLS peer. Forwarding a browser token to the gateway, or exposing the signing key to a browser, would defeat the gateway's trust boundary.
* **Reasoning/privacy loss:** AG-UI has reasoning events and OpenAI has reasoning summaries, but term2 intentionally sanitizes persisted public payloads. Do not forward raw chain-of-thought, credentials, absolute paths, or unbounded tool arguments merely to satisfy a client schema.
* **Protocol drift:** AG-UI, OpenAI, A2A, MCP, and ACP v2 evolve independently; historical ACP is archived. A facade must pin a version, validate schemas, and have a conformance test. “OpenAI-compatible” or “AG-UI-compatible” should describe the tested subset, not imply parity with the private gateway.

## Smallest viable interoperability experiment (no implementation in this note)

Build a throwaway, BFF-side AG-UI adapter against a fixture term2 gateway, using the official `@ag-ui/client` `HttpAgent` and a minimal CopilotKit/AG-UI rendering harness. Keep the experiment outside the production route table. Exercise this exact sequence:

1. Authenticate as one BFF user and select one read-only workspace; create a term2 session.
2. Send a two-turn text conversation and verify AG-UI text/run events map to the same term2 transcript and `turnId`s.
3. Trigger a tool approval, answer it once, reject it once, and trigger `ask_user`; verify the adapter preserves interaction ID, revision, safe choices, and terminal outcome.
4. Trigger reasoning, a subagent event, an abort, and one retry/compact command; verify unsupported features are visibly marked rather than represented as successful assistant text.
5. Disconnect during a stream, reconnect using the adapter's stored term2 cursor, and compare the resulting projection with a clean replay. Force a compacted cursor and verify the adapter requests a session reload.
6. Attempt cross-user/session/workspace access, stale interaction resolution, read-only write, malformed event payload, and forged client tool result; all must be rejected without runtime side effects.

**Go:** all ordinary chat and the approval/question flows work through the AG-UI client; event order and terminal outcomes match term2; reconnect either resumes exactly once or produces an explicit reload; no test bypasses BFF auth, owner checks, workspace boundaries, or read-only policy; unsupported commands/settings are not silently accepted.

**No-go:** any approval can be bypassed, any read-only session writes, a reconnect duplicates or loses a terminal event, a client can select another user's session/workspace, or the adapter must expose signing credentials. Also no-go for replacing the private gateway if more than the documented reduced chat subset is needed and preserving the missing semantics requires client-specific private extensions.

If AG-UI passes, adopt it as an optional BFF-facing compatibility contract and keep the native gateway for ChatForge/term2-specific controls. Separately consider an OpenAI facade only for generic chat clients, and A2A/MCP only for their respective agent↔agent and model↔tool use cases.

An ACP v2 experiment should pass only if an actual ACP client can create/resume a term2 session, render text/tool/plan updates, complete a permission request, and preserve the selected workspace and read-only/read-write policy through the adapter. It should fail if it requires exposing signing credentials, treats an editor's `cwd` as authorization without workspace validation, or silently converts a term2 interaction into an ordinary message. This is intentionally a second interoperability track: ACP v2 can improve editor/agent packaging, but it does not answer the user's immediate “reuse an existing web client” question.
