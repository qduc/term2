# Comparison with Term2 and recommendation

**Recommendation: adapt the ownership principles; do not replace Term2 with this
prototype.** The simulation supports one conversation owner and explicit
continuations for the brief's in-memory concurrency behaviors. It does not
establish production contract parity, physical cancellation safety, or simpler
real-provider integration. Adopting a wholesale rewrite from these results would
be unsupported.

The production comparison is against baseline `36d30a5c`. Evidence comes from
the implementation symbols below, the repository's
[submission contract](../../docs/contracts/01-conversation-submission-and-turn-lifecycle.md),
[continuity/effect contract](../../docs/contracts/02-provider-input-continuity-and-effect-settlement.md),
and the executable scenarios. Historical unit-test citations in those contracts
were not treated as current passing evidence. Production behavior was inspected,
not reimplemented or tested head-to-head.

## Evaluation metrics

| Metric | Prototype observation | Term2 observation | Interpretation |
| --- | --- | --- | --- |
| Conceptual complexity | Six domain concepts: submission, turn continuation, operation identity, canonical history/anchor, background job, event journal; mailbox is the serialization mechanism | Contract 01 names seven enforcement components across queue/admission, adapter identity/settlement, status leases, coordinator, run loop, input mailbox, UI projection; continuity additionally needs debt, ledger, input planning, and recovery policy | Scope-dependent count, not a complexity score. Prototype removes lifecycle handshakes; production covers more behaviors |
| State ownership | One runtime object can mutate submission status and active phase; ports/observers receive copies | QueueController owns queue state; ConversationAdapter owns payloads/settlement and cancellation proof; TurnStatusMachine owns status lease; TurnInputMailbox owns pending steering | Distributed responsibilities, not evidence that several components write the same field. Prototype centralizes lifecycle, but large future extensions could make it a god object |
| Cancellation coordination | One command → one transition; identity revoked before one foreground abort request; jobs have independent controllers | `ConversationAdapter.abort` invokes turnFlow and queue cancellation; `TurnCoordinator.abort` calls workflow, approval, status, continuity, and turn closure; `TurnWorkflow.abortLiveRun` waits for completion | Production earns part of this complexity by proving settlement before admitting potentially overlapping effects. Prototype merely fences stale results |
| Steering coordination | One admission record; `#requestModel` consumes it or `#finish` returns it | `ConversationAdapter.steerActiveTurn` → `TurnCoordinator.steer` → `TurnWorkflow.steer` → client/run loop → `TurnInputMailbox.offer`/`admitAtRequestBoundary` | Fewer ownership crossings in the prototype; production forwarding depth alone does not prove a defect |
| Code complexity | Single runtime file; separate simulation and measurement scripts | Declared 11-file comparison basket spans queue, adapter, workflow, run loop, continuity, input planning, ledger and recovery | Exact physical/nonblank counts are generated by `metrics.ts` and retained in evidence. The basket includes absent capabilities, so no percentage reduction or equal-contract LOC claim is valid |
| Observability | Sequence + session/turn + tokens + explicit failure/settlement events; deterministic trace replay comparison | Structured routing/recovery logs plus persisted user/tool/approval/assistant events | Prototype traces are easier to correlate locally, but lack persistence, wire evidence, streaming, and production redaction guarantees |
| Extensibility | Adding an ordering scenario requires a named harness function; mutation fix added one immutable routing capture, no lifecycle state | New behavior can cross queue, session, run loop, history, provider and UI boundaries depending on its contract | Evidence of local changes for these cases only; no measured team comprehension or future maintenance advantage |

Counts are intentionally reproducible rather than used as a correctness proxy.
The same implementation supports all eight requested capabilities, but the
meaning of “same behavioral contracts” stops at the explicitly simulated subset.

## Contract mapping

| Existing guarantee | Prototype mechanism / evidence | Missing guarantee or weaker behavior |
| --- | --- | --- |
| C1.1 stable submission identity | One map keyed by caller ID; duplicate rejection; concurrent-arrivals | No durable identity, recovered queue, cross-process uniqueness |
| C1.2 distinct lifecycle states, stale lease rejection | Submission status + workflow phase + unique token; approval/cancellation ordering matrix | No activating/prepared lease, compaction, UI or continuation projection |
| C1.3 exactly-once request promise settlement | At-most-once event settlement for every terminal submission; success/retract/cancel/fatal-failure scenarios | Public API is event-based, not promise-compatible; queued work, approvals and unknown outcomes deliberately remain pending until acted upon |
| C1.4 UI projections follow domain events | Independent observers can derive status, survive another observer throwing | No UI consumer, durable replay subscription, or observer backpressure |
| C1.5 steering survives turn/segment gaps | Target turn on queued submission, one request-boundary drain, release on finish; retry/next-boundary/final-boundary scenarios | No streaming segment/compaction gap; events don't expose a separate steer receipt promise |
| C2.1–3 paired history, paid tool debt | Only request model after full batch settlement; cancellation synthesizes unknown/not-executed results; every captured request checked for complete pairs | No durable ledger merging, compaction, parallel tool streaming, or provider-side debt validation |
| C2.4 and C2.7 safe unchained recovery | Failure drops anchor; next request has canonical history including completed tool results and admitted steer | Port always receives full history and an optional anchor hint. | C2.5 dispatched ambiguity vs undispatched abort | Tool rejection pauses as unknown; explicit reconciliation records outcome without dispatch; cancelled-tool scenario records unknown then not-executed | A cancelled adapter can still physically run. ## What the experiment changes our understanding of

An open turn does not require a currently running provider segment: retry,
approval, and reconciliation are retained continuations. Keeping steering next
to that continuation removes the need to coordinate segment-open and turn-open
flags. This is a useful candidate for a bounded production simplification.

Operation identity and physical cancellation are separate obligations. The actor
solves stale-state admission with a local comparison, but does not solve effects
that continue after revocation. Term2's cancellation-proof path is essential
complexity until equivalent evidence exists in an alternative.

Unknown execution outcomes, call/result debt, surviving job ownership, and history
provenance remain necessary regardless of the actor vocabulary. The independent
review's mutable-port defect also shows that message passing alone does not
enforce ownership: policy must not depend on an object handed to another owner.

The next justified production experiment would consolidate submission/steering
ownership behind an existing public boundary while preserving cancellation proof,
durable settlement and provider contracts. It should be compared against the
actual process/provider journeys, including partial stream output, reconnect,
compaction, and continuing mutating tools. That follow-up is a recommendation,
not implemented or approved here. If it cannot reduce coordination while keeping
those guarantees, reject the larger architectural change.
